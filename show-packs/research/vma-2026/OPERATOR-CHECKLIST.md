# 2026 VMAs — operator checklist and rollback path

The P3 deliverable named in `ROADMAP.md` ("write the show-specific operator checklist and
rollback path"), written for one host running a remote game of four to ten players from a
laptop plus their phone, with no developer on call.

Companion documents: [`BRIEF.md`](BRIEF.md) (decisions D1-D10, rehearsal list, risks),
[`AUTHORING-NOTES.md`](AUTHORING-NOTES.md) (what is in the pack and what is unverified),
[`../../README.md`](../../README.md) (activation), `RUNBOOK.md` (live-ops doctrine),
`AGENTS.md` (the protected list).

## How to read this document

**Every command says which database it touches.** Scripts print the target before they do
anything: `target: local  http://127.0.0.1:54321` or `target: PRODUCTION  https://....supabase.co`.
Read that line every time. The defaults are not uniform:

| Command | Default target | How production is selected |
| --- | --- | --- |
| `compile-show-pack`, `generate-settlement-drop`, `simulate-results-night` | no database at all | n/a |
| `activate-show-pack`, `issue-operator-capability`, `prepare-settlement`, `settle-room`, `export-settlement-receipt`, `restore-room-snapshot`, `repair-room-message` | local | `SUPABASE_TARGET=remote` |
| `gm-pulse`, `sentinel`, `snapshot-game`, `companion-daemon` | **production** | already remote; `SUPABASE_TARGET=local` to aim them at the local stack |

**Protected actions** (from `AGENTS.md`) are flagged in every step below. They are: applying
migrations to the live project; deleting or truncating any table; running any script against a
room that real people are in; `npx vercel --prod` and alias changes; rotating or touching
credentials; and anything that writes pack-owned `categories` rows. Pack activation writes
pack-owned `categories` rows, so **every `activate-show-pack --apply` is protected, local or
not** — a stray practice row leaks into every room bound to that pack.

**Credentials.** For the remote target the scripts read `.env.local` only — exporting
`SUPABASE_SERVICE_ROLE_KEY` in your shell does **not** work. Before Friday, `.env.local` must
carry `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` and
`ANTHROPIC_API_KEY`. `.env.local` is gitignored; keep it that way. For the local target the
service key comes from `supabase status` automatically.

**Paths used below.** Authoring pack:
`show-packs/research/vma-2026/vma-2026-authoring.json`. Compiled bundle:
`show-packs/compiled/vma-2026.json`. Private operator files live under `.private/`
(gitignored): capabilities in `.private/operator-capabilities/`, snapshots in
`.private/snapshots/`, settlement worksheets in `.private/settlements/`.

Replace `CODE` with the real four-letter room code everywhere. Room codes are generated by the
app when you create the room; you do not choose them.

## 1. Thursday: rehearsal on the local stack

Nothing here touches production. The only protected step is 7, because it writes pack-owned
catalog rows. Budget two to three hours. Do the whole thing once; a rehearsal you skipped is
the step that will fail on Sunday.

### 1.1 Bring the local stack up

**Database: local. Not protected.**

```sh
supabase start
```

Proves it worked: `supabase status -o json` returns JSON containing
`"API_URL": "http://127.0.0.1:54321"`. (That is the exact value `scripts/lib/env.mts` reads;
the human-readable banner text varies with the CLI version, so check the JSON.)

**Database: local. Destructive to the local database only** — it drops every local room,
player and message. Nothing on production is touched, but do not run it if you still need a
local rehearsal room.

```sh
supabase db reset
```

Proves it worked: the next command in 1.3 prints `target: local  http://127.0.0.1:54321` and
`[show-pack-activation] catalog=planned` — that is, the reset database has no VMA catalog rows
left over from an earlier rehearsal.

**Database: local. Not protected.** The reset replays every migration, including
`20260921000100_ten_player_keepsake_verdicts.sql`, which raises the post-show keepsake packet
from seven rows to ten. This room seats up to ten, so run the keepsake dogfood against the
freshly reset database before anything else touches it:

```sh
npx tsx scripts/dogfood-companion-claims.mts
```

Proves it worked: `target: local  http://127.0.0.1:54321` at the top, then a final `PASS` line
with no `FAIL` above it. The lines that matter for this room are the full-room keepsake packet
ones — the racing-host election, `a losing host tab cannot write any keepsake row`, and
`every durable keepsake row carries the exact grounding provenance`. If instead you see
`keepsake verdicts require one through seven bounded rows`, the local database is running an
older schema: the reset did not replay the new migration. Stop and fix that before Friday,
because production will behave the same way.

### 1.3 Create a rehearsal room and activate the pack into it

**Database: local. Not protected.** Start the dev server and create the room in a browser —
there is no script that creates rooms. The app mints the room, the host seat and the first
operator capability in one transaction.

```sh
npm run dev
```

1. Open `http://localhost:5173`, tap **Create Room**, enter your name, pick an avatar.
2. The app shows a four-letter code. Write it down. That is `CODE`.
3. Leave the room in the lobby. Do not tap "Start the Party" yet — activation requires a lobby
   room with no pack-dependent game state.

**Database: local. Read-only preflight, not protected:**

```sh
npx tsx scripts/activate-show-pack.mts \
  --input show-packs/compiled/vma-2026.json \
  --room CODE
```

Proves it worked:

```text
[show-pack-activation] room=CODE pack=vma-2026@1 id=…
[show-pack-activation] predictions=23 entities=67 beats=12 bingo=46
[show-pack-activation] portraits=67 verified=true
[show-pack-activation] runtime_model=legacy_ensemble fact_source=scheduled
[show-pack-activation] activatable=true; no rows written
```

`runtime_model=legacy_ensemble` is the Results Night shell. If it says
`conviction_portfolio`, the game contract is wrong and the night will be the wrong game.

**Database: local. PROTECTED — writes pack-owned `categories` rows.** The command requires the
room code twice; that double confirmation is the mechanism, and you are the human confirming

```sh

  --input show-packs/compiled/vma-2026.json \

```

Proves it worked: `[show-pack-activation] bound CODE to vma-2026@1 model=legacy_ensemble`.
Anything short of that line, including `catalog=draft-partial`, means the pack is still a draft
and the room is not bound.

### 1.4 Issue the operator capability and open the private link

**Database: local. Read-only status check, not protected:**

Proves it worked: `[operator-capability] room=CODE issued=true` followed by

**Database: local. PROTECTED — this is a credential.** Because one already exists, issuing


Proves it worked:

```text

[operator-capability] phone_link_file=/…/.private/operator-capabilities/CODE.url
```

Open the link:

```sh
cat .private/operator-capabilities/CODE.url
```

Paste it into the host browser. It lands on `/room/CODE/live#operator=…`; the app-shell strips
the fragment before any room screen opens and stores the bearer under that room's ID. While
the room is still in the lobby, navigate back to `http://localhost:5173/room/CODE` after the
link has loaded once.

Local caveat: a loopback origin only works on the laptop. For the Thursday rehearsal the
"second phone" is a second browser profile (or a private window) with devtools device mode set
to **375 by 812**. Use a real phone only against the deployed production origin (section 2).

### 1.5 Walk BRIEF section 7 with two clients

**Database: local. Not protected.** Work through the brief's rehearsal list in order and write
down what you actually ran:

1. Lobby with both clients seated; host taps **Start the Party**.
2. Both clients tap **Got it**; the countdown fires when everyone is ready.
3. Timed draft: let one client's 45-second turn expire and confirm the turn advances.
4. Confidence: make ranked picks on both clients; host taps **Start the show**.
5. Live: declare three categories through **Spotlight** → tap winner → **Confirm Winner**.
6. Try the undo on one of them (see section 4.6 — read that before you rely on it).
7. Open and close one spotlight without declaring.
8. Bingo: deal, mark, unmark, complete a line.
9. Run the daemon against the local room in a second terminal:
   `SUPABASE_TARGET=local npx tsx scripts/companion-daemon.mts --room CODE`
   Proves it worked: `[cast HH:MM:SS] bingo watch live — N existing marks baselined` and
   `[cast HH:MM:SS] chat watch live — N messages baselined, answering as of now`.
   Know the limit of this rehearsal: `scripts/lib/env.mts` loads `ANTHROPIC_API_KEY` only for
   the **remote** target, so a local daemon has no model credential and every generation
   attempt fails (logged as `transient: …`). What you are proving locally is the lease, the
   heartbeat and the two watch loops — not that the cast writes good lines. The cast itself is
   first exercised for real on Sunday, which is why section 4.4 checks it three times.
10. Reload the host phone mid-live and confirm every scheduler recovers.
11. Walk every player route at 375 by 812 and confirm no page says House of the Dragon,
    dragon, Oscars or Film Encyclopedia (acceptance criterion 9), and that the header names
    the 2026 MTV Video Music Awards rather than "Watch Party".
12. Declare the remaining categories and close the live floor (section 4.10).

### 1.11 If the machine has no Docker

All of section 1 assumes `supabase start`, which needs Docker. A Docker-free stand-in exists at
`.private/local-stack/` (gitignored, sandbox-only, never production): real Postgres 16 with all
65 migrations and `supabase/seed.sql` applied, real PostgREST, and a shim answering
`supabase status -o json` on the same `http://127.0.0.1:54321`. Bring it up with
`.private/local-stack/start.sh`, put `.private/local-stack/bin` first on `PATH`, and pass
`SUPABASE_TARGET=local`. Its `README.md` lists what is real and what is not — the important
absences are Realtime, the auth server, Storage, Vault and every `supabase db …` subcommand, so
any rehearsal step that depends on a broadcast reaching a second phone still needs a real stack
or a real pair of phones. Pack activation and the operator scripts do work against it: the VMA
pack has been activated into a room there end to end.

Proves it worked — one row, `status` published, and all three identity fields non-empty:

### 2.8 Apply the ten-player keepsake migration

**Database: production. PROTECTED — this applies a migration to the live project. Ask the user
and get an explicit yes before running it. Do not run it on a day a room is live.**

Skip this entirely if the room will seat seven or fewer. Above seven it is not optional: the
keepsake command demands the *complete* room player set, so with eight or more players every
attempt is rejected and the room finishes with no keepsake at all rather than a partial one.

`supabase/migrations/20260921000100_ten_player_keepsake_verdicts.sql` is additive — it only
relaxes the row bound on `complete_grounded_player_verdicts` from seven to ten and its packet
ceiling from 30000 to 45000 bytes. It adds no column, changes no signature, and every packet
the old definition accepted the new one still accepts.

Check first what is actually pending, and confirm the target line says PRODUCTION:

```sh
npx tsx scripts/schema-diff.mts
```

Then, only after the user has said yes:

```sh
supabase db push
```

Proves it worked: `supabase db push` lists
`20260921000100_ten_player_keepsake_verdicts.sql` as applied and exits 0, and a re-run of
`npx tsx scripts/schema-diff.mts` reports no drift between local and production.

If you decide not to apply it, say so out loud and cap the room at seven players. A bundle
deployed in 2.1 against an unmigrated database is safe — a ten-player room simply fails with
the old, readable `keepsake verdicts require one through seven bounded rows` — but it fails
every time, and Monday's settlement will have no keepsakes in it.

## 3. Draft night: Sunday 5:00 p.m. ET, with a Saturday practice draft

The real draft is Sunday at 5:00 p.m. ET on a call: ten players over four snake rounds is
about forty minutes at the timer's pace, which lands the draft by 5:45 and leaves ninety
minutes for everyone's picks before the 7:15 lock. One pregame event is easier for strangers
to commit to than a Saturday session plus a Sunday show. The cost is recovery time, so run a
throwaway practice draft on Saturday with two or three friends in a practice room; that is
also the rehearsal your laptop timing forces onto Saturday. Whoever is in the lobby when you
start the Sunday draft is in the game.

The draft is a live, synchronous event even though the show is not. Put everyone on a call.
Nothing in this section is a script; it is all the app.

1. **Before anyone joins**, confirm the room still reads `phase lobby` and the VMA identity is
   on screen. `npx tsx scripts/gm-pulse.mts --room CODE` (production, read-only).
2. **Share the join link, or the site link and the four-letter code.** The join link is your site
   link with `/join/CODE` on the end (`/?join=CODE` also works, for anything that mangles paths).
   It opens the landing page already in the join state with the code filled in and the room
   looked up; the player still types a name and taps join, so a tap can never seat somebody by
   accident. Still **not** a `/room/CODE` link: a player with no seat who opens that one is
   bounced to the landing page. A phone that already has a seat in a different room is asked
   which room it wants rather than being redirected away from your link.
3. **Wait for everyone.** The draft order is randomized the instant the host taps **Start the
   Party**, from exactly the players seated at that moment. Someone who joins afterward is not
   in the draft at all. Count heads on the call first.
4. **Ready-up.** Every player taps **Got it**. When the last one is ready, the host's tab
   writes the shared countdown and all phones move together.
5. **The timed draft.** 45 seconds per pick, snake order. When a turn expires, the host's tab
   advances it automatically — so the host tab must stay open, awake, and holding the
   capability for the whole draft. Be honest with the room about what that means: **an expired
   turn is skipped, not auto-picked.** That player simply loses the pick.
6. **The last pick is deliberately never auto-skipped.** If the player holding the final pick
   walks away, the draft stalls and there is no host button to force it. Before the draft
   starts, tell everyone the last pick belongs to a real person who has to tap it.
7. **Confidence picks** open as soon as the draft completes. Players rank every category. They
   can do this any time between the draft and the 7:15 p.m. ET lock — the picks are sealed until lock.
8. **A player who joins late or lost their phone: seat reclaim.** Entering the *exact* same
   name (case and surrounding spaces ignored) on the join form reclaims the existing seat with
   its original sigil. Two seats with the same exact name refuse automatic reclaim — the app
   says so and asks the host which seat is theirs. A genuinely new name in a started room is
   rejected; there is no way to add a player after the draft, and that is intentional.
9. **What the host must not do:**
   - Do not write a room phase directly from the browser console or a script. Every phase
     command is capability-gated and a direct write fails closed; trying it only wastes time.
   - Do not navigate a player to another route to "move things along". Phase change is the only
     thing that moves everyone; `navigate()` from a user action breaks the shared transition.
   - Do not run `ghost-screen`, any `dogfood-*` script, or `supabase db reset` against
     production. The dogfoods refuse remote targets, but a mis-set `SUPABASE_TARGET` is still
     the fastest way to ruin a real room.
   - Do not rotate the operator capability after the practice draft unless the bearer leaked. Rotation
     bumps the room revision and disables the host's controls until the new link is opened.
   - Do not apply a migration. Not before the show, not during it.

### Who is in the game

**One thing is genuinely broken, and it is a race of a few seconds.** If someone taps the final
**Join Room** button at the same moment you tap **Start the Party**, their seat can land in a room
that has already frozen its draft order. The app checks the phase and then inserts, and nothing
between those two steps holds the room still (`src/hooks/useRoom.ts:157` reads the phase,
`src/hooks/useRoom.ts:168` writes the seat). The draft order was fixed from exactly the players
seated at the instant you started (`supabase/migrations/20260813000300_optional_identity_ceremony.sql:232`
— "draft order must contain every room player exactly once"), so that seat is not in it. What you
get is a half-player: they are on the roster and in the head count, they can chat, they get a
bingo card and they show on the leaderboard, but they never get a turn in the draft and end with
no artists at all. Worse, while the room is in pre-draft the countdown waits for *everyone* on the
roster to tap **Got it** (`src/pages/Room.tsx:209`), so if that phone wanders off, the draft never
starts and there is no host override. **Practical protection: count heads on the call, tell people
to be joined and idle before you start, and look at the "N joined" number one more time as you tap
Start.** If it does happen, the room is recoverable — see 6.2 — but the cleanest live answer is to
have that person reclaim their seat by name after the draft and accept that they have no roster.

The smallest fix, not implemented: one additive migration adding a `before insert` trigger on
`players` that refuses a new seat when the room's phase is past `lobby`, modelled on
`guard_chosen_faction_player_join` (`20260813000300_optional_identity_ceremony.sql:160-186`), with
`service_role` exempt for repair. It would make the database enforce what the app already refuses,
and it cannot affect seat reclaim, because reclaim adopts an existing row and never inserts. Before
landing it, re-run `dogfood-show-pack-activation.mts` and `dogfood-roster-sync.mts`: both insert
post-lobby seats on purpose and assert the current error text.

Everything below is the ordinary behavior, and it is safe to paste into the invite.

**Before the draft starts (room in the lobby):** anyone with the code or the join link is in. They
pick a name and a sigil, and their seat is waiting whenever they come back.

**After you tap Start the Party — through the draft, the confidence picks and the whole live
show:** a *new* person cannot join. The app looks the room up and shows the join form as usual, so
the link still works, but it says "This room is underway. Enter the exact name you used before"
and the button becomes **Find My Seat** (`src/pages/Home.tsx:820`). A name nobody in the room is
using is refused outright with "This game has already started. To reclaim your seat, join with the
exact name you used before" (`src/hooks/useRoom.ts:157`). No player row is written. They get no
draft roster, no confidence picks, no bingo card, no leaderboard row, and they are not in the
chat. They can still watch the room from the outside only after the show, through the public recap
link.

**Someone who was already in and lost their phone:** they type the *exact* name they used, and the
app adopts their existing seat with its sigil, draft roster, picks and bingo card intact
(`src/hooks/useRoom.ts:137-155`). Case and surrounding spaces are ignored. Two seats sharing one
exact name refuse automatic reclaim and tell them to ask you which is theirs
(`src/hooks/useRoom.ts:145`).

**What the database would allow, which is why the head count matters.** The refusal above is the
app's, not the database's. `players` accepts any insert (`supabase/migrations/00000000000000_baseline.sql:463`,
`players_insert ... with check (true)`), and the only insert trigger that blocks a post-lobby seat
applies to shared-banner rooms, which this VMA room is not — its contract is
`exclusive_entity_draft` (`20260813000300_optional_identity_ceremony.sql:174-177`). The other
trigger, `guard_closed_players`, only bites after settlement
(`20260810190300_freeze_closed_score_inputs.sql:35`). So a seat that does get in late by the race
above behaves like this: draft picks are rejected because the seat is not in the frozen order
(`20260810192100_atomic_draft_pick.sql:108`); confidence picks work and your lock auto-fills them
at random rather than stalling (`src/hooks/useConfidence.ts:370`); a bingo card is dealt normally,
since dealing is allowed in every phase up to the close of the live floor
(`20260812062000_bingo_seat_authority.sql:62-69`); chat is fully open; and they appear on the
leaderboard, because it is computed over the roster rather than over who drafted
(`src/lib/scoring.ts:255`).

**There is no player cap anywhere.** Not a column on `rooms`, not an RLS policy, not a line of
lobby copy — the lobby only counts up ("N joined") and only enforces a *minimum* of two
(`src/pages/Room.tsx:255`). The ten in "four to ten players" is a limit of the offline simulator
and of the post-show keepsake packet, not of the room. Nothing stops an eleventh person joining;
what happens to them is untested.

### 6.4 If the pack itself is wrong mid-show

**You cannot rebind a live room.** The database only permits binding a published pack to a room
that is still in the lobby with no pack-dependent game state. Once the draft has happened, the
pack the room is bound to is the pack you are playing. Recompiling, re-activating, or editing the
authoring file changes nothing about tonight, and a published pack cannot be upserted.

- Do not attempt a catalog repair against production during a show. That path exists, it takes a
  service role and a registry lock, and it is not a thing to do on a phone at 8:40 p.m.
